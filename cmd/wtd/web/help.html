terminal help

Findings that make this terminal less surprising. The list grows: when one of these screens confuses someone, the answer lands here.

Shift+Enter submits instead of adding a line

This terminal sends the exact same byte for Enter and Shift+Enter, so the program on the other end — Claude Code, any REPL — cannot tell them apart and treats both as "send". That is a property of the terminal, not a setting you can change in the program.

To add a line without sending, in Claude Code:

  • Ctrl+J — its universal newline key, works in any terminal.
  • \ then Enter — also works everywhere.
  • Option+Enter (macOS) or Alt+Enter — this terminal does send a distinct sequence for those.
Closing the tab doesn't stop the session

Sessions live on the server, independent of this page. Closing the tab, losing wifi, even the server itself restarting — what runs in the session keeps running. The reconnect button (or reopening the same link) rejoins it, and the recent output the server holds is replayed. That buffer even survives a service restart — though not a reboot — and what it can never show is output printed while the server was down; the replay says so when that gap exists.

What does end a session: exit in its shell, or killing it from the session list. The banner tells you which happened — it says "session ended" when the shell exited, and "the session is still running" when only the connection dropped. In the first case the button starts a new, empty session under the same name, and says so: nothing is left to rejoin.

Ctrl+\ drops every browser and app viewer of the session

Ctrl+\ is the detach key. In a session it disconnects every viewer connected through this server — not just you — though the session keeps running and anyone can rejoin. (A viewer attached from a shell with dtach -a stays.) The foreground program never receives it as a signal; to quit a program, use its own quit key instead.

Clicking a URL does nothing — hold Cmd or Ctrl

URLs in output are links: hovering underlines one and shows its target in the corner, and Cmd+click (macOS) or Ctrl+click opens that target in a new tab, leaving this session connected. The modifier is deliberate: a plain click is how you select text, and inside a program that watches the mouse — Claude Code, editors — it is a message to that program. So a plain click never opens anything.

Trust the corner readout, not the underlined text: a program can label a link with one URL and point it at another. And this is a desktop gesture — a phone browser has neither hover nor a modifier key, so there, select and copy the URL instead.

Two devices on the same session name share one screen

Opening the same session from a laptop and a phone shows one shared terminal: both see all output, and both can type, interleaved. That is the point — start something at a desk, check it from a phone. For a private terminal, create a session with a different name.

Scrolling back doesn't reach output from before you connected

Two different buffers are in play. While you are connected, your browser keeps its own scrollback of what arrived (currently ten thousand lines). From before you connected, the server replays a bounded amount of recent output on attach; anything older than that buffer happened, but this page never received it and cannot show it.

Scrolling inside Claude Code feels laggy, and nothing here can fix it

In a full-screen program — Claude Code, less, an editor — there is no local scrollback to move. Your scroll becomes a message to that program, which redraws its whole screen and sends the result back. Every visible step is a round trip over the network, so it stays slightly behind your finger no matter how fast this page is.

Plain shell scrollback is different, and does feel smooth: that content is already in your browser, so nothing is sent anywhere. What you are feeling is which of the two you are scrolling, not a setting you can change.

A terminal on your own machine works exactly the same way and only feels better because its round trip is microseconds instead of milliseconds. Faster drawing and coarser scroll steps are already done here; fewer, larger round trips are still round trips.

The tab icon changes colour on its own

The favicon is a status light for whatever agent is running in that session, so a row of identical-looking tabs tells you which one wants you:

  • Cyan circle — working.
  • Amber diamond — finished its turn; your move.
  • Red triangle — blocked, waiting on you to answer something.
  • Grey prompt — idle, or nothing is reporting.

The icon carries the state; the tab's title carries the identity — the session name and whatever the program running in it set as its title, which for an agent is usually the task it is working on. If that title starts with a spinner or status symbol of its own, it is dropped: it animates several times a second and repeats what the icon already says.

Nothing detects this — the program running in the session says so, by writing one escape sequence to the terminal. From anything that still has the terminal (a shell prompt, a wrapper script) that is one line:

printf '\033]1337;WTState=%s\a' waiting > /dev/tty

The states are running, waiting, attention and clear.

From an agent's hook, that line silently does nothing, and this is the trap worth knowing before you wire one up. Claude Code — and any agent that captures its hooks' output — runs them with no controlling terminal at all, so /dev/tty cannot be opened and the write is discarded without an error. Standard output is no better: the agent captures it into the transcript.

A hook has to address the terminal by path instead: walk up /proc from the hook to the first ancestor whose stdout is a /dev/pts/* — that is the terminal the agent itself is drawing to — and write there. ~/.claude/tmux-attention.sh on this box is a working example, wired to PreToolUse and UserPromptSubmit for running, Stop for waiting, Notification for attention, and SessionEnd for clear.

With no such line anywhere, a background tab still turns red when a program rings the terminal bell. That is a guess rather than a report, so it clears the moment you look at the tab, and any session that sends a real status is trusted over its own bells.

What the ≡ panel shows, and why memory can look fine on a dying box

The button beside ? slides out a reading of the machine itself: load average, memory, disk, how long it has been up, and what each session is costing. It floats over the terminal rather than shrinking it, so opening it never resizes anything or makes a full-screen program repaint. It only asks the server while it is open and this tab is in front.

Read the stall row first. Free memory is a bad early warning: Linux counts reclaimable cache as available, so a box minutes away from becoming unreachable can still report gigabytes free. The stall figures are the share of the last ten seconds in which something was actually blocked waiting for memory, CPU or disk — memory stall starts climbing while the free figure still looks survivable. not measured means this kernel does not report it, which is not the same as zero.

The load average is shown next to the CPU count because it means nothing without it. A load of 8 is idle on 64 CPUs and fatal on 2.

Sessions are listed heaviest first, and the one you are attached to is in bold. Each figure adds up the memory of every process in that session, so an agent and everything it has started count together. Pages shared between processes are counted more than once, so read the numbers as an upper bound and as a way to compare sessions rather than as an exact total. There is no limit on how many sessions you can start: this list is how you notice that the answer is nevertheless finite.

Starting, finding, and sharing sessions

The session list shows every session and creates new ones. A session's link is this server's address plus ?arg=name — it attaches if the session exists and creates it if not, so the link is safe to bookmark or send to another of your devices before the session exists.
